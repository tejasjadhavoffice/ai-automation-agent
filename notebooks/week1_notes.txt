Week 1 — Prompt experiment 
Setup :
- Same request for all three runs: "Read file python_info.txt"
- Command: python -m app.main --mode once --prompt-style <style> --request "Read file sample.txt"
- Ran from project root, sample.txt kept next to app folder.

Zero-shot
What I saw:
- Model had only the system prompt + my user line. No example JSON in the user message.
- It picked read_file like I wanted. The JSON in the output had path sample.txt and tool ran ok.
- One time the reply had a bit of extra text before the JSON but the code still found the { } part so it did not crash.

My takeaway:
- Fast and simple. For a clear request like "read this file" zero-shot was enough.
- If the model ever returns messy JSON, zero-shot has no example to copy from so I rely more on our parser.

Few-shot

What I saw:
- Prompt included one example (read file -> JSON with tool_name read_file). So the model had a pattern to copy.
- Same tool read_file again. Felt like the JSON shape was more stable — arguments looked like what I expect every time.

My takeaway:
- I liked this best for this undersgtandin. One example makes the format obvious and I worry less about invalid JSON.

Chain-of-thought (cot)
What seen:
- User message had the short "think then output JSON" line before my request.
- In the printed llm_response_text I still mostly see JSON only (our system prompt says JSON only). So CoT did not add a long essay for me; maybe the "thinking" is inside the model but not shown much in text.

My takeaway:
- For this simple task CoT did not feel different from zero-shot in the final result.
- I will use CoT when the user request is confusing or has many parts, not for a single "read file" line.


Conclusion (which worked best for this request)

For "Read file sample.txt" after my three runs:
- Best for me: few-shot — example in the prompt matched our tool JSON and felt safest.
- Zero-shot: fine for obvious tasks; I keep it for quick tests.
- CoT: ok to try on harder prompts later; for this file read it was not a big win.
